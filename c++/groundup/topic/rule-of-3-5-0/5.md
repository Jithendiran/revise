## The Rule of Five

The Rule of Three (destructor + copy constructor + copy assignment) extended to C++11 by adding move semantics:

> **If a class requires any one of the five special member functions, it almost certainly requires all five.**

| Function | Signature | Purpose |
|---|---|---|
| Destructor | `~T()` | Release the resource |
| Copy constructor | `T(const T&)` | Deep copy into new object |
| Copy assignment | `T& operator=(const T&)` | Deep copy into existing object |
| Move constructor | `T(T&&) noexcept` | Transfer ownership into new object |
| Move assignment | `T& operator=(T&&) noexcept` | Transfer ownership into existing object |

The same reasoning from the Rule of Three applies: needing any one of these signals that the class manages an external resource. That resource requires correct behavior from all five paths.

### Compiler Generation Rules — The Full Matrix
The compiler generates default versions of the five special functions under specific conditions. User-defined declarations suppress generation.

| User declares | Destructor | Copy ctor | Copy assign | Move ctor | Move assign |
|---|---|---|---|---|---|
| Nothing | Generated | Generated | Generated | Generated | Generated |
| Destructor | User | Generated* | Generated* | NOT generated | NOT generated |
| Copy constructor | Generated* | User | Generated* | NOT generated | NOT generated |
| Copy assignment | Generated* | Generated* | User | NOT generated | NOT generated |
| Move constructor | Generated* | NOT generated | NOT generated | User | NOT generated |
| Move assignment | Generated* | NOT generated | NOT generated | NOT generated | User |
| Destructor + copy ctor | User | User | Generated* | NOT generated | NOT generated |
| All five | User | User | User | User | User |

When a programmer writes a custom destructor, the compiler triggers a specific safety warning system regarding copy operations.

#### The Historical Problem
In older versions of C++, if a programmer wrote a custom destructor, the compiler still automatically generated copy constructors and copy assignment operators.

This behavior caused severe software bugs. If a class requires a custom destructor, it almost always manages a raw resource (such as dynamic memory). Automatically generating copy operations for such classes leads to shallow copies, where two distinct objects attempt to manage and delete the exact same memory address. This results in program crashes.

#### The Modern C++ Standard (The Warning)
To fix this historical flaw, modern C++ standards (starting from C++11) declare that relying on the compiler to automatically generate copy operations when a custom destructor is present is deprecated.
* Why it still happens: The compiler still generates them to ensure that millions of lines of legacy software written before the year 2011 do not suddenly break and fail to compile.
* Why it is discouraged: Modern software engineering rules state that if a class requires a custom destructor, the programmer must explicitly declare or delete all copy and move operations to prevent accidental memory corruption.

Note on Asterisks ($\ast$): In standard language specifications, functions marked with an asterisk are deprecated if a destructor is user-defined, but the compiler will still implicitly generate them unless explicitly deleted or suppressed.

#### Underlying Logic and Principles
The generation or suppression of special member functions follows strict compiler safety rules. The compiler follows these laws to prevent catastrophic runtime errors, such as memory corruption or double-free crashes.

1. **The Destructor Rule**
    * Logic: If a developer writes a custom destructor, it means the class manages a raw resource (such as dynamic memory, a file handle, or a network socket) that the default cleanup behavior cannot handle.
    * Consequence: Because a custom destructor signals complex resource management, the compiler disables the automatic generation of move constructors and move assignments (NOT generated). The compiler assumes that a simple member-wise move would cause multiple objects to point to the exact same raw resource, leading to double-deletion crashes.
    * Legacy exception: Copy operations remain implicitly generated (marked with $\ast$) for backward compatibility with older C++ codebases, though this practice is deprecated.
2. **Copy Constructor and Copy Assignment Rules**
    * Logic: Copy operations are independent of each other in terms of user declaration. Declaring a custom copy constructor does not automatically block the compiler from generating a copy assignment operator, and vice versa.
    * Consequence: If a user defines a custom copy constructor, it implies that the default shallow copy is inadequate (usually requiring a deep copy due to raw pointers). Consequently, the compiler blocks move operations (NOT generated) because it cannot safely guess how to implement a high-performance move operation without explicit developer instruction.  
3. **Move Constructor and Move Assignment Rules**
    * Logic: Move operations transfer resource ownership rather than duplicating data.  
    * Consequence: If a developer explicitly writes a custom move constructor or move assignment, it signals that the class manages unique resources. Defining either move operation suppresses the implicit generation of all copy operations (both copy constructor and copy assignment become NOT generated). The compiler deletes them because an object that supports unique ownership transfer should typically not permit indiscriminate copying. A move operation does not suppress a destructor. Instead, the presence of a custom destructor or resource-handling logic requires the developer to explicitly manage all related special functions.

#### Underlying Logic of the Rule of Five
The Rule of Five is a programming guideline stating that if a class defines a custom destructor, copy constructor, copy assignment operator, move constructor, or move assignment operator, the developer must explicitly define all five of them.

1. **Why Move Operations Suppress Copy Operations**
    * Logic: A move operation transfers the ownership of data from one object to another without duplicating it.
    * Consequence: If a developer explicitly writes a move constructor or move assignment operator, it indicates that the object manages unique resources. The compiler automatically disables (suppresses) the generation of copy operations to prevent the accidental duplication of unique resources.
2. **Why Custom Destructors Suppress Move Operations**
    * Logic: A destructor is responsible for releasing resources when an object is destroyed.
    * Consequence: If a developer writes a custom destructor, it signals that the default cleanup behavior is insufficient. The compiler automatically disables move operations because the default move behavior cannot safely handle complex resource cleanup without explicit instructions.  
3. **Developer Responsibility**
   * Logic: The compiler safety mechanisms are designed to block unsafe automatic code generation.
   * Consequence: When a class manages a raw resource, the developer cannot rely on default compiler behavior. The developer must supply a custom destructor and all corresponding copy and move functions to ensure memory is allocated, transferred, and destroyed correctly without causing system crashes.

#### `= default`
When a destructor or copy operations are user-defined, the compiler suppresses move operations. `= default` explicitly restores them:

```cpp
class Config {
    std::string data;

public:
    ~Config() {
        std::cout << "Config destroyed\n";
    }

    // Destructor suppressed move operations — restore them explicitly
    Config(Config&&) noexcept = default;
    Config& operator=(Config&&) noexcept = default;

    // Restore copy operations too (destructor left them as deprecated)
    Config(const Config&) = default;
    Config& operator=(const Config&) = default;
};
```

### `= delete` — Prevent Moving

Some resources cannot be transferred. A mutex cannot be moved — it is a synchronization primitive tied to a specific memory location.

```cpp
class MutexGuard {
    std::mutex& mtx;
public:
    MutexGuard(std::mutex& m) : mtx(m) { mtx.lock(); }
    ~MutexGuard() { mtx.unlock(); }

    // Moving a lock guard makes no sense — the lock is on a specific mutex
    MutexGuard(MutexGuard&&) = delete;
    MutexGuard& operator=(MutexGuard&&) = delete;

    // Copying also makes no sense
    MutexGuard(const MutexGuard&) = delete;
    MutexGuard& operator=(const MutexGuard&) = delete;
};
```
